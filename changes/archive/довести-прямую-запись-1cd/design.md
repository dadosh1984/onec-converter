# Design — производственная надёжность записи в 1CD (Фаза 16)

## Цель

Сделать прямую запись (`load_direct`/`append_records`) безопасной для
практики: верификация после записи, атомарный replace (без «полузаписи»),
ясные ошибки лимитов, чистка tmp-копий (диск C: была переполнена).

## Текущее состояние

- `verify.py` — сверка полноты `verify(source_objects, target_objects)`
  по `(type, key)` и чексумме атрибутов (уже есть).
- `load_direct` — копирует исходник в `wd/1Cv8.1CD`, пишет строки в неё через
  `append_records`, возвращает `copy_path`. НЕ атомарно (пишет по месту).
- `append_records` уже: LockError (открытая ИБ), WriteError, если нет
  data_page, WriteError при превышении FAT-слотов (нужен fat_level 2).
  Нехватка диска (ENOSPC) не ловится явно.
- tmp-копии реальной базы (100+ МБ) накапливались на диске C: (заполнен) —
  нужна чистка.

## Подход

### 1. Атомарность (работа в tmp + atomic replace)
- `load_direct`: копировать исходник в `wd/work.1CD`, писать append**в него**,
  по завершении `os.replace(wd/work.1CD, wd/1Cv8.1CD)` — атомарная замена.
  `copy_path` остаётся `wd/1Cv8.1CD`. Сбой append → в wd остаётся недопис
  `work.1CD`, `1Cv8.1CD` не создан/не полузаписан.
- После успешного replace — `work.1CD` уже нет (переименован). При ошибке —
  удалить `work.1CD` (finally).

### 2. Верификация после записи
- Новый параметр `load_direct(..., verify_after: bool = True)`.
- После append прочитать записанные строки из финальной копии, свернуть в
  объекты `{type, key, attributes}` (декодирование по полям таблицы), сверить
  через `verify(objects, read_objects)`. Результат — в отчёте `verify`.
- Неполнота/ошибка чексумм → `verify.full == False` (не бросаем, возвращаем
  в отчёте; при желании пользователь обрабатывает).

### 3. Ясные ошибки лимитов/прерывания
- Нехватка диска: в `load_direct` поймать `OSError` (errno ENOSPC) при копии /
  append → `LoadError('недостаточно места на диске')`.
- Размер батча: опциональный `max_objects` (задокументировать, дефолт без
  лимита или разумный); превышение — LoadError с понятным текстом.
- Prевышение FAT-слотов (fat_level 2) и LockError — уже есть, документируем.

### 4. Чистка tmp
- После успешного replace work-файл уже переименован (нет). При исключении —
  `finally` удаляет `wd/*.1CD` некорректен copy? Осторожно: пользователь может
  захотеть сохранить `copy_path`. Разрешим: на ошибку удаляем только `work.1CD`
  (не трогаем 1Cv8.1CD исходник wd не создан). Задокументировать.

## Модули
- `src/onec_converter/load_8x.py` — атомарность, verify_after, ошибки лимитов,
  чистка.
- `src/onec_converter/load_8x_refs.py` — (при необходимости) reader строк→объект.
- `tests/test_load_8x_verify.py` — unit: verify после записи, (не)полнота.
- `tests/test_load_8x_atomic.py` — атомарный replace; ошибка ENOSPC не оставляет
  полузапись; нехватка tmp пишется/читается.
- `docs/zero-setup.md`, `docs/playbook.md` — раздел «Проверка копии перед
  использованием» (verify, атомарность, лимиты).
- `README.md` — краткая секция.

## Ограничения / риски
- verify читает ту же копию — подтверждает читаемость парсером, не «валидность
  для реальной 1С» (см. Фазы 14/15: индексы).
- Чистка tmp — не удалять финальный 1Cv8.1CD (в wd), удалять только work/мусор.
- Не менять публичный API совместимо (verify_after по умолчанию True).

## Верификация
- pytest (unit + e2e копия 8.1), ruff, mypy strict, vitest.
- e2e: load_direct реального объекта → verify.full True; при порче строки —
  verify.full False.
