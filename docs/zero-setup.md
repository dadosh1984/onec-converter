# Zero-setup на приёмнике — исследование (Фаза 4)

Цель: минимальное вмешательство пользователя при переносе. Пользователь, который
не знает 1С, не должен собирать/устанавливать расширение.

## Вариант A. Прямая запись в 1Cv8.1CD приёмника (собственный writer)
- Формат 1CD разобран нашим парсером (чтение). Запись требует:
  1. запись строк в таблицы (фиксированные/переменные поля, BLOB-цепочки 256-байт чанков);
  2. обновление каталога таблиц/страниц, индексов;
  3. согласованность системных таблиц (IBVERSION, журнал, счётчики);
  4. блокировку при открытой базе (файл 1Cv8.1CL) — запись только при закрытой ИБ.
- Риск: повреждение базы -> обязательная резервная копия и верификация (verify).
- tool1cd (GPL) доказывает принципиальную возможность записи; мы пишем свою
  реализацию (логика формата — из собственного парсера, без чужого кода).
- Приоритет: после стабилизации чтения (Фаза 5) и контракта load (Фаза 4 MVP).

## Вариант B. Автоустановка расширения через 1cv8.exe DESIGNER
- Требует платформы 1С на машине пользователя (нарушает «сервер без платформы»
  только для этапа подготовки приёмника; сам MCP-сервер остаётся без платформы).
- Команда: 1cv8.exe DESIGNER /F <база> /LoadExtensionCfg <файл.cfe>
  — расширение собирается один раз из исходников, далее авто-подключение.
- Подходит пользователям с установленной платформой; для остальных — вариант A.

## Вывод
- **MVP реализован (Фаза 13)**: вариант A — `load_8x.load_direct(target_dir,
  objects, workdir)` — прямая запись в КОПИЮ `1Cv8.1CD` приёмника без
  расширения; CLI `onec-converter load --direct <target-dir> --input <batch>`,
  MCP-тул `load_direct`. Оригинал никогда не изменяется (copy_1cd + LockError).
- Ограничения MVP: `_IDRREF` новых строк — префикс из существующих строк
  таблицы + счётчик (точная семантика 1С не гарантируется); индексы таблиц
  не пересобираются (Фаза 12); поддержаны простые реквизиты
  (NVC/NC/N/L/DT), ссылки — последующая работа.
- Вариант B (автоустановка расширения через DESIGNER) — дополнительный.

## Производственная надёжность записи (Фаза 16)

- **Верификация после записи**: `load_direct(..., verify_after=True)` (по
  умолчанию) после записи читает записанные строки через собственный парсер
  и сверяет «roundtrip без потерь» (перекодировка объекта должна дать те же
  байты). Результат — в отчёте `verify: {ok, checked, missing, mismatched}`.
  `verify.ok == True` ⇒ все объекты записаны и читаются без потерь.
- **Атомарность**: запись идёт во временный `work.1CD`, по завершении —
  атомарный `os.replace(work.1CD → 1Cv8.1CD)`. Сбой/прерывание не оставляет
  «полузаписанный» финальный файл; work-файлы удаляются.
- **Лимиты и ошибки**: `max_objects` (батч больше → `LoadError`); нехватка
  диска (ENOSPC) → `LoadError('недостаточно места на диске')`, work чистится;
  открытая ИБ → `LockError`; превышение FAT-слотов (fat_level 2) → `WriteError`.
- **Чистка tmp**: временные work-файлы удаляются в normal и при ошибке;
  финальный `1Cv8.1CD` в `workdir` не трогается (это и есть результат).

### Как проверить копию перед использованием

1. Вызвать `load_direct(..., verify_after=True)` (по умолчанию) — убедиться
   `rep['verify']['ok'] is True` и `checked == len(objects)`.
2. Прочитать полученную копию собственным парсером (`Database1CD(copy_path)`)
   и сравнить число строк с ожидаемым.
3. Ограничение остаётся: **индексы не пересобираются** (Фаза 14) — реальная 1С
   может не сразу видеть новые строки по индексируемым полям.
