# Идеи Фазы 6 — источники и обоснование

Принцип проекта: берём **только идею** из внешнего проекта, усовершенствуем её
и реализуем **авторским кодом** (сторонние библиотеки 1С не включаются).
Источники: 200 проектов 1С из `github_list.xlsx` (изучены README/описания) +
ранее изученные парсеры tool1cd/onec_dtools (зафиксировано в `format-8x.md`).

## Трек A — парсер и данные

| # | Идея | Источник | Реализация | Зачем нашему проекту |
|---|------|----------|------------|----------------------|
| A1 | **Кеш ссылок GUID→наименование** | tool1cd/onec_dtools («кеш ссылок») | `read_table(..., resolve_refs=True)`: REF-поля отдаются `{guid, name}` через lazy-кеш имён | Сейчас REF-поля — «сырые» GUID: читатель не понимает, на что ссылается запись («Банки»→банк без имени). С именами выгрузка становится человекочитаемой, упрощается аудит и сопоставление при переносе |
| A2 | **Размеры таблиц в status** | 1C_PrometheusExporter (72★), ClusterMonitoring — метрики | `status`-тул дополняется `table_sizes` (строки/байты на таблицу, лениво+кеш) | При переносе нужно понимать объём работы (какие таблицы большие, сколько записей). Без этого невозможно оценить время выгрузки и приоритеты |
| A3 | **Журнал метрик времени** | 1C_PrometheusExporter / БСП «Оценка производительности» (histogram, APDEX) | Лёгкий `Timings`: histogram read_metadata/read_table по типу объекта | Медленные операции видны сразу (как было в Фазе 5: 150s→1.7s). Метрики времени — основа будущей оптимизации и диагностики у пользователя |
| A4 | **CP1251→UTF-8 middleware** | Кодировки 7.7-источников (1Cv77.dat, CP866/CP1251) | Параметр коннектора `encoding`; перекодирование текстовых полей на стыке чтения | 7.7-базы — в CP866/CP1251, приёмник 8.x — UTF-8. Без прозрачного слоя «кракозябры» попадают в данные; middleware делает перенос 7.7→8.x корректным из коробки |
| A5 | **Генератор синтетической мини-1CD** | 1C-Company/dt-demo-configuration (демо-базы для тестов) | `build_fake_1cd(path, tables, rows)` — валидная маленькая файловая база | unit-тесты парсера сейчас требуют реальных баз по 2.5 ГБ. Генератор даёт детерминированные фикстуры — тесты быстрые, воспроизводимые, без гигантских файлов |

## Трек B — конвертация

| # | Идея | Источник | Реализация | Зачем нашему проекту |
|---|------|----------|------------|----------------------|
| B1 | **TYPE_PRIORITY** | 1cdtools «TYPE_PRIORITY» | Детерминированный порядок типов Str < Num < Date < Bool < Ref; `resolve_type_priority(types)` | При конвертации поля с составным типом надо однозначно выбрать целевой тип. Сейчас выбор неявный; приоритет делает его предсказуемым (аналог `_DBNAME_PRIORITY` из Фазы 5) |
| B2 | **TOON — таблица соответствий** | Конвертация данных 3 (TOON — таблица соответствия объектов и реквизитов) | JSON-правила маппинга «источник→приёмник», валидация, применение в `transform.py` | Жёсткие маппинги в коде не настраиваются пользователем. JSON-правила позволяют перенастраивать перенос без изменения кода (для каждого клиента свои правила) |
| B3 | **Импорт правил обмена КД3** | otymko/gitrules (71★) — разбор XML правил конвертации | Парсер XML правил «Конвертации данных 3» → JSON-TOON | Экосистема 1С уже имеет тысячи готовых правил обмена (XML). Возможность их импорта спасает пользователя от ручного описания маппинга |
| B4 | **Анонимизатор PII** | Маскирование персональных данных (общая практика) | `anonymizer.py`: маскировка ФИО/телефонов/ИНН по regexp/списку реквизитов | Перенос данных между средами (прод→тест) требует обезличивания. Без анонимизатора персональные данные утекают в тестовые базы |

## Не взято (и почему)

- **vanessa-automation / xUnitFor1C / yaxunit** — тесты на BSL внутри 1С; наш проект — Python, тесты уже на pytest.
- **deployka / vanessa-runner / 1C-Deploy-and-CopyDB** — управление платформой 1С через RAC/RAS; наш MCP работает напрямую с файлами (read-only), платформа не нужна.
- **1C_Sentry / Sentry_1C** — отправка ошибок в Sentry из 1С; ошибки нашего пайплайна уже логируются через MCP-ответы.
- **bsl-parser / bsparser / 1c-syntax** — парсеры кода BSL; мы не анализируем код, только данные и структуру.
- **OpenIntegrations (660★)** — интеграции с внешними API из 1С; у нас обратное направление — MCP наружу.
- **GitConverter целиком** — синхронизация хранилища конфигурации; взята только идея выгрузки метаданных в текст (D1).
- **liteExchange / FoxyLink** — фреймворки обмена внутри 1С; промежуточный формат у нас уже есть (`intermediate.py`).
