# Форматы источников 1С 8.x — результаты спайка

> Статус: подтверждено на реальной базе `1C_8.1` (файл `1Cv8.1CD`, 2,5 ГБ, 517 таблиц).
> Заголовок файла: `1CDBMSV8` + `08 03 08 00` → **формат 1CD 8.3.8.0**
> (конфигурация внутри — 8.1-эпоха: GUID-файлы метаданных).

## Чтение: библиотека onecreader (1creader, MIT)

Формат 1CD 8.3.8.0 полностью читается через **`onecreader`** (github.com/vengeoff/1creader,
MIT). Основан на `onec_dtools` (Infactum) и `tool1cd` (e8tools). Это готовая read-only библиотека:
заголовок, страницы, объекты БД (FAT level 0/1), таблицы, blob-цепочки (256-байтные чанки).

- `raw1cd.Database1CD(path)` — открытие; `ib.tables` — dict имя→TableDef; `ib.table_rows(t)` — строки;
  `ib.read_blob(t, first_chunk, size)` — blob.
- Типы полей: `NVC` (utf-16le, префикс длины), `RV` (ссылка = 16 байт GUID), `N` (BCD-подобное число),
  `DT` (7 байт дата), `L` (булево, 1 байт), `B`/`I` (бинарные).
- **Кодировка данных 8.x — UTF-16LE/UTF-8** (не CP866, как 7.7).

## Таблицы базы

- Системные: `CONFIG`, `CONFIGSAVE`, `PARAMS`, `FILES`, `DBSCHEMA`, `IBVERSION`, `V8USERS`, …
- Данные: `_REFERENCE3…` (справочники, 62 шт), `_DOCUMENT39…` (документы, 136 шт),
  `_INFORG…` (регистры сведений, 23 шт), `_ACCUMRG…` (накопления, 2 шт), `_ENUM101…` (перечисления, 29 шт),
  `_ACCRG…` (бухгалтерия), `_ACC2` (план счетов), `_CKINDS…` (виды расчётов), `_VT…` (табличные части).
- Табличная часть объекта — отдельная таблица `_REFERENCE<id>_VT<nn>`.

## Конфигурация в 1CD (8.1-эпоха)

- Таблица `CONFIG` — 4648 файлов метаданных: имя = GUID, содержимое zlib-сжато (inflate).
- Файл `root` = `['2', <main_guid>, <base64>]`; файл `<main_guid>` — дерево конфигурации:
  узлы коллекций `[class_guid, count, guid1, guid2, …]`; class_guid → тип объекта
  (`metaids.TOP_COLLECTIONS` — совпал для 8.1-эпохи: 62 Справочник, 136 Документ и т.д.).
- **Файл объекта 8.1-эпохи** (на примере справочника «Банки»):
  ```
  ['1', ['47', <guids…>, ['0',['0',['0','0',<self_guid>]], <имя>, ['1','ru',<синоним>], <коммент>], …]]
  ```
  Имя и синоним — на месте (`Банки` / `Банки и МФО`). Открытый вопрос спайка — полный layout
  реквизитов и табличных частей (для имён атрибутов).

## DBSCHEMA

- Таблица `DBSCHEMA`, поле `SERIALIZEDDATA` (blob, 449 КБ) — текстовое описание схемы БД.
- Блок: `{"ReferenceN","N",<id>,"",{<поля>}}`; поля: `FldNNN` с типами
  `R` (ссылка, таргет-таблица), `N` (число: длина, точность), `S` (строка), `L`, `E` (перечисление), `V` (версия).
- **Привязка таблица ↔ объект — НЕ по порядку коллекции!** Авторитетный источник — таблица
  **PARAMS, файл `DBNames`** (inflate, UTF-8-SIG): `{<total>, {<count>, {<guid>,"Reference",<num>}, …}}`.
  Для базы 8.1-эпохи: 5762 записи; kinds → префиксы таблиц:
  `Reference` (62) → `_REFERENCE<N>`, `Document` (136) → `_DOCUMENT<N>`, `Enum` (29) → `_ENUM<N>`,
  `InfoRg` (23) → `_INFORG<N>`, `AccumRg` (2) → `_ACCUMRG<N>`, `Acc` (1) → `_ACC<N>`,
  `CKinds` (1) → `_CKINDS<N>`, `VT` (180) → `_VT<N>`, `Const` (17) → `_CONST`.
  Проверено: «Банки» (guid 8496674d-…) = Reference **3** = `_REFERENCE3` (1141 запись);
  «Валюты» (6c1501cf-…) = Reference **5** = `_REFERENCE5` (5 валют: USD, RUB, EUR, UZS).
  Номер в имени файла объекта (node47[17]) НЕ является номером Reference!
  Синонимы в DBSCHEMA пустые — имена берём из конфигурации.

## Решение по интеграции — АВТОРСКИЙ КОД (философия проекта)

> Правило проекта: **пишем свой код с нуля**. Чужие проекты/библиотеки в проект НЕ включаются.
> Чужие проекты (tool1cd, onec_dtools, 1creader и др.) — только для ИЗУЧЕНИЯ логики формата;
> берём идеи, улучшаем (качество, скорость, производительность), код пишем свой.

- **Собственный 1CDBMSV8-парсер пишем САМИ** (изучив логику tool1cd / onec_dtools / 1creader).
- Формат подтверждён на реальных базах (см. выше) — риски изучены, приступаем к реализации.
- `.spike/1creader` — только исследовательский инструмент, в поставку не входит.

## Приёмник 1С 8.3 (изучен: `1C_8.3`)

- Файл `1Cv8.1CD` — формат 1CD 8.3.8.0 (тот же, что источник 8.1). 8033 таблицы.
- Конфигурация: **«Бухгалтерия для Узбекистана, редакция 3.0»** (определено по `DoNotCopy.txt`),
  данные отсутствуют (приёмник пустой).
- Именование таблиц 8.3 — camelCase: `_Reference74`, `_ReferenceChngR1731` и т.д.
  (в 8.1-эпохе было `_REFERENCE3`). Парсер обязан принимать оба стиля.
- Новые системные таблицы: `CONFIGCAS`, `CONFIGCASSAVE`, `DEPOTFILES`, `SCHEMASTORAGE`.
- Формат хранилища конфигурации 8.3 (GUID-файлы vs ConfigDumpInfo) — открытый вопрос спайка.
- Запись в приёмник — через расширение конфигурации с HTTP-сервисом (без прямой записи в .1CD).

или нет. Запасной коннектор source_8x_dt не реализован (честный статус: не исследован).

### Файл объекта 8.1-эпохи — layout (спайк)

`['1', ['47', <8 GUID>, ['0',['0',['0','0',<self_guid>]], <имя>, ['1','ru',<синоним>], <коммент>],
  '2','0',['0','0'],'1','0','1','1','5','1','70','1', …]]`

Расшифровано:

## Спайк 5.1 — низкоуровневый каталог и строки (подтверждено на `1C_8.1`)

Проверено на реальной базе (1CD 8.3.8.0, 310108 страниц по 8192 б, locale `ru_RU`):

### Root-объект и каталог таблиц
- Root-объект БД — страница 2: сигнатура `1c fd`, `fat_level` (0/1), длина (uint64 @16),
  FAT-таблица номеров страниц с `PAGE_HEADER_SIZE=24` до конца страницы.
- Данные root-объекта — цепочка blob-чанков по **256 байт**: заголовок чанка
  `[nxt:uint32][size:int16]` + payload `size` байт.
- Каталог таблиц — цепочка от чанка **1**: `[locale:32s][count:int32][offsets: count×int32]`
  (517 таблиц; locale `ru_RU`); каждый offset — чанк с **UTF-8 описанием таблицы**.
- Описание таблицы:
  ```
  {"<NAME>",0,
  {"Fields",
  {"<field>","<type>",<null_exists>,<length>,<precision>,"<case>"},...
  },
  {"Indexes",...},
  {"Recordlock","0"},
  {"Files",<data_page>,<blob_page>,<index_page>}
  }
  ```
  Пример (фрагмент `_REFERENCE3`): `_IDRREF` B16, `_VERSION` RV, `_MARKED` L, `_ISMETADATA` L,
  `_PARENTIDRREF` B16, `_FOLDER` L, `_CODE` NC5, `_DESCRIPTION` NVC70, `_FLD174…` NVC (null=1).

### Раскладка полей строки
- RV-поле (версия) — всегда на **offset 1** (16 байт). Остальные поля — последовательно,
  начальный offset 17 при наличии RV, иначе 1.
- Размер поля: `B=length, L=1, N=length//2+1, NC=length*2, NVC=length*2+2, RV=16, NT=8, I=8, DT=7`;
  при `null_exists=1` добавляется **1 байт флага** (0x00 = null, 0x01 = значение).
- NVC с null: `[flag:1][len:uint16][utf-16le: len*2][padding пробелами до длины поля]`.
  NC: фиксированная строка utf-16le, паддинг пробелами `20 00`.

### Строки и blob
- Строки таблицы — данные `read_object(data_page)` (цепочка страниц FAT), нарезка по `row_length`.
  `_REFERENCE3`: data_page=2405, row_length=797, **1141 запись** (банки Узбекистана):
  `_CODE='00002'`, `_DESCRIPTION='Банки РУз'` и т.д. Папки (`_FOLDER`), пустые слоты — на месте.
- Blob таблицы: `read_object(blob_page)` → цепочка чанков 256 б от `first_chunk*256`
  (заголовок `[nxt:uint32][size:int16]`), сборка до `size` байт.
- DBSCHEMA: таблица `DBSCHEMA`, поле `SERIALIZEDDATA`; строки `[flag:1][off:uint32][size:uint32]`
  (строки с flag=0x01 — пропуск); blob → **UTF-8-SIG** текст (~449 КБ).

### CONFIG (конфигурация 8.1-эпохи)
- Таблица `CONFIG`: поля `FILENAME`(NVC), `CREATION`(DT), `MODIFIED`(DT), `ATTRIBUTES`(N),
  `BINARYDATA`(8 б: off+size), опц. `PARTNO` (в 8.1-эпохе ОТСУТСТВУЕТ — размер по умолчанию 0).
  Строки с flag=0x01 — пропуск. BINARYDATA → blob → **zlib raw inflate** (`zlib.decompress(-15)`).
- Содержимое файла — «скобкофайл» UTF-8 (BOM): `{a,b,{c,d},"строка"}`, кавычка экранируется удвоением;
  корень `['2', <main_guid>, <base64>]`; файлы объектов `['1', ['47', …]]` (имя, синоним `['1','ru',…]`).
- `CONFIGSAVE` — наложение поверх `CONFIG` (ожидающие изменения метаданных); для 8.1-эпохи пусто.
- Привязка: порядок Reference-блоков DBSCHEMA = порядок GUID коллекции = порядок таблиц
  `_REFERENCE3…` (см. выше).

## 8.3-эпоха: скобкофайлы, escape-формат, DBNames (расшифровано на `1C_8.3`, 8.3.8.0)

### Строковые литералы: экранирование и суррогаты UTF-16

В скобкофайлах 8.3 строки — UTF-8, кавычка внутри строки экранируется **удвоением `""`**
(как в 8.1); `\"` — это обычные backslash+кавычка, НЕ escape-последовательность
(подтверждено примером `(Испания)\"` и BSL-кодом `""\""` = `Код + "\" + …`).

Последовательность **`\` + 4 hex-цифры** — это UTF-16 code unit (2 байта big-endian).
Декодируются **только суррогаты 0xD800–0xDFFF**; все прочие значения (RTF-команды `\deff0`,
пути `root\default`) остаются как есть — это просто текст.

Суррогатная пара может быть **разорвана кавычками**: 1С сериализует один символ как
`"часть1"\d83c"\df10часть2"` (high-суррогат в одном литерале, low — в соседнем).
Парсер склеивает соседние строковые литералы без запятой (`parse_list`) и объединяет
high+low в один символ (`_merge_surrogates`). Итог по конфигурации 8.3: всего 23 вхождения
`\`+4hex — 6 суррогатов (3 пары, файлы с префиксом `67b8886f…`) и 17 не-суррогатов
(RTF `\deff`, `\defa`) — эмодзи 🌐 в каракалпакском синониме декодируется корректно.

### Не-скобкофайлы в конфигурации

Почти все GUID-файлы конфигурации — скобкофайлы (UTF-8 BOM + `{`). Исключение — 2 файла
(`3b83e71b…0` — 3 751 289 Б и `a413de50…0` — 721 Б) с **JSON-данными**
(`{"data":[{"lgotaId":100407,…}`); их «базовые» ключи без суффикса `.0` — валидные
скобкофайлы (202/177 Б). Парсер пропускает файлы, начинающиеся с `{` + кавычка (JSON),
а их скобкофайлы-базу читает как обычно. 33436 из 33438 файлов 8.3 — скобкофайлы.

### MOXCEL-контейнер

Часть файлов конфигурации — бинарные **MOXCEL**-контейнеры (табличные документы/макеты):
сигнатура + длина + payload; внутри — нарезка на скобкофайлы-объекты. Для переноса данных
не требуется — только для чтения макетов (вне текущего скоупа).

### DBNames 8.3 и привязка объект ↔ таблица

Таблица `DBNames` (8.3): 36 378 записей. Поля `Kind` (строка): Fld=30721, LineNo=1377,
Enum=796, InfoRgChngR=777, ByDims=596, ConstChngR=498, ReferenceChngR=490, DocumentChngR=359,
ByField=203, ByProperty=158, ByResource=123, AccumRgOpt=122, ScheduledJobs=85,
DocumentJournal=24, Node=20. **Kind='Reference' в 8.3 отсутствует** (это 8.1-стиль).

Один GUID встречается в DBNames **дважды**: основной таблицей (`{"Reference",74}`) и таблицей
изменений (`{"ReferenceChngR",1731}`). Словарь строится с приоритетом: главные kinds
(Reference/Document/Enum/InfoRg/…) = 100, таблицы изменений (…ChngR) = 10 —
при дубле GUID побеждает основная таблица (`_DBNAME_PRIORITY`).

Скобкофайл объекта 8.3 (справочник): `[1, [56, guid1…guid5], 5, [3daea016…, 0], …]` —
число 56 — это **тип-код** (не номер таблицы; таблицы Reference начинаются с 74),
а привязка идёт через DBNames по GUID. Имена объектов 8.3: `['0', ['2', ['1','0',guid],
'ИМЯ', ['2','ru',синоним], …]]` (обёртки счётчиков версий, отличные от 8.1-формы
`['0', ['0', guid, имя, …]]`).

### Производительность (оптимизации ускорения)

Полный прогон интеграционных тестов на реальных базах (8.1 + 8.3) сокращён
с 8–10 минут до ~3.5s (холодный кеш) / ~1s (тёплый). Три оптимизации в
`source_8x_file.py`:

1. **Ленивая распаковка конфигурации.** `read_config()` распаковывал все
   47 648 файлов 8.3 (zlib inflate ≈ 3.5s). Теперь строки CONFIG/CONFIGSAVE/PARAMS
   читаются один раз без blob-данных (`_load_config_rows` — только указатели
   FILENAME/смещение/размер), а blob читается и распаковывается по запросу
   (`config_get(name)` с индексом `имя → (таблица, смещение, размер)` и кешем
   распакованных). `read_metadata` использует ~2.5k из 47.6k файлов → inflate ~0.2s.

2. **Частичный разбор скобкофайлов** (`_object_name_fast`). Полный `parse_bracket`
   строил дерево целиком (4.3M вызовов `parse_value`, 41M append — 7.3s на 2545
   объектов 8.3). Ленивый парсер разбирает только префикс до имени/синонима
   (корневой список → второй элемент → первый подходящий `['0', sub, …]` до
   `sub[3][2]`), остальное пропускается сканнером `_skip_value` без построения
   дерева — 0.17s, результат идентичен полному парсеру (253/253 и 2545/2545).

3. **Дисковый кеш метаданных** (`read_metadata` → `.onec_cache/`, ключ
   `file_key` из cache.py: путь + размер + mtime_ns + первые 64 КБ). Повторные
   вызовы для неизменённой базы — миллисекунды; mtime/размер/первые 64 КБ
   защищают от устаревания.

Итог: `read_metadata` 8.3 — 1.7s первый вызов, 0.013s из кеша; 8.1 — 0.08s.

### 1Cv8.dt (8.x) — статус исследования

Приоритет низкий: основной формат источника 8.x — живая файловая ИБ 1Cv8.1CD

(не zlib-контейнер). При наличии реального .dt — разбор по логике сообщества
(tool1cd/onec_dtools), решение: переиспользовать 1CD-парсер после распаковки
или нет. Запасной коннектор source_8x_dt не реализован (честный статус: не исследован).
