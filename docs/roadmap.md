# Roadmap — фазы 7–11

Продолжение после Фазы 6 (все фазы 1–6 закрыты, `changes/archive/`).
Принципы неизменны: авторский код с нуля, реальные базы read-only,
ворота mypy strict / ruff / pytest (и vitest .ts-сниппеты для Orion).

Порядок: Фаза 7 (сквозной перенос — даёт первый полный сценарий) →
Фаза 8 (XLSX-отчёты — быстрый выигрыш) → Фаза 9 (CLI — доступ без MCP) →
Фаза 10 (запись в 1CD — самый рискованный шаг) → Фаза 11 (новые идеи).

## Фаза 7 — Сквозной перенос 7.7 → 8.3 (интеграция)

Цель: первый полный сценарий переноса — 7.7 (cp866/cp1251) → intermediate →
TOON-правила → transform → validate → загрузка в приёмник 8.3. Сейчас каждый
коннектор тестируется отдельно, сквозного теста нет.

- [x] [spike] Пайплайн end-to-end: потоки данных между шагами
      (init → inspect → extract → map → transform → validate → load):
      форматы батчей, точка стыковки Base77/read_table ↔ intermediate ↔
      HTTP-приёмник; зафиксировать в docs/pipeline.md
- [x] [fact] Интеграционный тест полного переноса на синтетике:
      gen_dat (7.7, cp866) → правила TOON → HTTP-mock приёмника 8.3;
      проверка количества записей, ссылок, кодировок
- [x] [fact] Тест CP1251-варианта сквозного переноса: cp1251 → UTF-8
      доходит до приёмника без искажений (A4 middleware в пайплайне)
- [x] [assumption] MCP-сценарий переноса: один тул `migrate(...)` —
      последовательность шагов пайплайна с прогрессом и timings
      (или пошаговые вызовы с проверкой pipeline_status)
- [x] [assumption] README: раздел «Сквозной перенос 7.7→8.3» с примером
      команд агенту (Claude/Cursor)

## Фаза 8 — XLSX-отчёты структур

Цель: закрыть обещанный в C2 (Фаза 6) XLSX-отчёт и добавить отчёт размеров
таблиц; используем готовый `xlsx_report.py`.

- [x] [fact] `xlsx_report.py`: функция отчёта compare_structures —

- [x] [assumption] MCP-тул `structure_report(source_dir, target_dir, out_file)`:

- [x] [assumption] Отчёт размеров таблиц: `table_sizes` → XLSX

      листов, заголовков, строк (включая кириллицу и пустые структуры)
- [x] [assumption] Интеграционная проверка на реальных базах 8.1/8.3
      (read-only): отчёт формируется, размеры совпадают с table_sizes

## Фаза 10 — Прямая запись в 1CD 8.3

Цель: загрузка данных в приёмник 8.x без расширения (сейчас — только
HTTP-расширение). Самый рискованный шаг: парсер read-only; запись требует
точного формата (FAT, цепочки, BINARYDATA). Работаем только на копиях.

- [x] [spike] Формат 1CD 8.3 на запись: что необходимо для создания новой
      базы / добавления записей в существующую (root, каталог таблиц,
      FAT level 0/1, цепочки блоков, SERIALIZEDDATA); риски целостности;
      зафиксировать в docs/format-8x.md (раздел «Запись»)
- [x] [assumption] `write_8x.py`: создание новой пустой базы 1CD
      (копия структуры приёмника: таблицы, поля, индексы)
- [x] [assumption] Вставка записей в существующие таблицы:
      добавление строк в конец, обновление размера таблицы и FAT
- [x] [fact] Unit-тесты: созданная база читается собственным парсером;
      записанные строки декодируются обратно без потерь
- [x] [assumption] Интеграционный тест на КОПИИ 8.3-базы (tmp):
      копия исходника → запись тестовых записей → чтение парсером
- [x] [assumption] README/docs: документация формата записи + ограничения
      (только копии, не оригиналы)

## Ворота для всех фаз

```
pytest                      # unit + интеграционные (реальные базы — read-only копии)
ruff check src tests
mypy src
npx vitest run              # .ts-сниппеты для Orion shield
```

Каждая фаза открывается в Orion (think → draft → ручная доводка design/tasks),
закрывается shield + out (SUCCESS, guard allPass), затем архивируется
в `changes/archive/`.

## Фазы 12–16 (закрыты)

Фазы, добавленные после 7–11, реализованы и заархивированы
(`changes/archive/`):

- **Фаза 12** — хвосты записи: fat_level 1 (объекты >8 МБ), indirect-страницы,
  защита записи (`LockError`), обратная совместимость.
- **Фаза 13** — zero-setup A: `load_8x.load_direct` — прямая запись в КОПИЮ
  `1Cv8.1CD` без HTTP-расширения; `copy_1cd`, `append_records`.
- **Фаза 14** — индексы (spike, Вариант A): reverse-engineering показал старый
  image-формат объекта индекса (отличен от Tool1CD); битовая упаковка ключей
  не расшифрована, запись вслепую небезопасна → **реализация НЕ выполнялась**,
  ограничение «индексы не пересобираются» задокументировано (`docs/format-8x.md`,
  раздел «Индексы (Фаза 14, spike)»).
- **Фаза 15** — документы: REF-поля (`_FLD...RREF` → `_IDRREF` приёмника по
  естественному ключу), реквизиты документа (`_NUMBER`/`_DATE_TIME`/`_POSTED`),
  табличные части (`_<Base>_VT<num>`, parent + `_LINENO`); ref-warnings.
- **Фаза 16** — надёжность записи: `verify_after` (roundtrip без потерь),
  атомарный replace (`work.1CD` → `os.replace`), лимиты (`max_objects`, ENOSPC),
  чистка tmp; как проверить копию — `docs/zero-setup.md`.
- **Инфраструктура**: ворота — `bash scripts/gates.sh` (pytest+ruff+mypy+vitest);
  тесты больших баз — `E:\test` / `ONEC_TEST_TMP` (см. `pytest.ini`).

Статус на конец фаз 14–16: **проект ≈98–100%** (см. `docs/backlog.md`,
`docs/ideas.md`). Остались только опциональные пункты блок-листа.
